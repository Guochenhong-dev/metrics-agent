# 项目讲解与面试准备

## 项目到底解决什么问题

运营人员问“最近收入为什么下降”，首先需要明确“收入”指支付额、退款冲抵后的净实收，还是会计收入；还要确定日期、区域及对比周期。未经统一口径就生成图表，很容易给出看似合理但实际不可复核的结论。

本系统把流程固定为：**问题 → 结构化计划 → 口径/权限/范围校验 → 前期对比 → 维度拆解 → 证据解释 → 报告**。默认可以不调用模型，先验证完整的计算链路；启用模型后，由模型辅助理解问题与组织解释。

## 模块和技术

| 模块 | 用到的技术 | 代码入口 | 具体职责 |
| --- | --- | --- | --- |
| 指标目录 | Java静态定义、固定聚合视图 | MetricCatalog | 定义指标名称、公式、单位、时间字段及限制 |
| 计划解析 | 规则解析；可选Spring AI结构化输出 | PlannerService | 生成指标、维度、日期、单值筛选计划 |
| 查询校验 | 白名单、服务端权限、日期边界 | PlanValidator | 拒绝非法维度、越权区域及过大周期 |
| SQL执行 | Spring JDBC、参数绑定、超时与预算 | QueryEngine | 从固定视图生成聚合SELECT，不执行模型SQL |
| 数据计算 | BigDecimal、SQL聚合、只读事务 | AnalysisEngine | 对比、比例、贡献、趋势和阈值提醒 |
| 模型解释 | Spring AI Tool Calling、结构化输出 | NarrativeService | 读取已授权证据，输出待验证解释 |
| 结果缓存 | 有界本机缓存、可选Redis | ResultCache | 按权限、计划、版本缓存计算结果 |
| 报告 | Jackson、数据库持久化、CSV/Markdown | ReportService | 保存快照、导出、历史权限复核 |
| 网页图表 | 原生JavaScript、ECharts | static/app.js | 计划表单、趋势、贡献、筛选重查 |
| 登录 | Spring Security、BCrypt、Session、CSRF | SecurityConfig | 认证、角色限制、区域权限映射 |

本版是单体应用，未使用LangChain、向量数据库、微服务注册中心或独立MCP服务。第三个项目重点是受控经营分析，与第二个售后Agent的业务流程不同。

## 指标口径

| 指标 | 计算方式 | 时间字段 | 注意事项 |
| --- | --- | --- | --- |
| 净实收 | 支付成功金额－实际退款金额 | 支付按支付日，退款按退款日 | 现金流口径，不是会计确认收入 |
| 支付额 | 支付成功金额之和 | paid_on | 后续退款不改写历史支付额 |
| 退款额 | 退款金额之和 | refunded_on | 可对应更早创建、支付的订单 |
| 订单量 | 创建订单总数 | created_on | 包含取消和待支付订单 |
| 取消率 | 已取消创建订单数/创建订单数 | created_on | 订单状态取数据快照最终状态 |
| 履约率 | 已履约创建订单数/已支付创建订单数 | created_on | 近期订单可能尚未到履约观察期 |

订单状态维度和筛选也取快照中的状态，不是“支付发生当时的状态”。如果未来接入状态事件流，需要额外定义状态生效时点，不能直接复用这里的口径。

## 核心计算是怎样完成的

钱在数据库中用整数“分”存储。SQL先求和，Java用BigDecimal换算成元。比例不对每行百分比取平均，而是先汇总分子、分母，再做除法。

对比周期为紧邻当前周期的前一等长周期。例如2026-08-25至08-31共7天，对比08-18至08-24。跨月时仍按LocalDate逐日计算，不假定一个月30天。

相对变化的约定为：

`(当前值 - 前期值) / abs(前期值) × 100%`

这里对净实收可能为负的情况使用前期绝对值作分母，报告必须结合绝对金额解读。基期为0时结果为null，不用“增长100%”替代。

### 金额/订单量的变化贡献

某区域贡献 = 该区域当前值－该区域前期值。所有区域贡献相加，应等于整体变化。

例：华东减少10元，华北减少50元，总体减少60元。华东贡献率约16.67%，华北约83.33%。如果有一个区域增加、另一个减少，贡献率可以为负，也可以超过100%；它不是份额占比。

### 比例的变化贡献

不能直接把各区域“取消率变化”相加。系统采用：

`区域贡献（百分点） = 100 × 当前区域分子/当前总体分母 - 100 × 前期区域分子/前期总体分母`

所有区域贡献之和等于总体比例的变化。它是分子占总体分母份额的变化分解，不是因果分解，也不是将“组内比率效应”和“权重效应”分别剥离的专业计量模型。

当前总体或前期总体分母为0时，不进行比例贡献分解。总变化为0时，贡献率也为null。

## 查询安全为什么不依赖模型“听话”

- 模型只输出Plan，Plan中没有SQL字段。额外JSON字段会被拒绝。
- 表名、指标公式、时间字段均来自服务端目录。
- group by字段只能从区域、品类、渠道和订单状态四个键中选择。
- 日期、区域与筛选值用PreparedStatement参数绑定。
- 每一条聚合SQL都会附加登录用户的授权区域条件，客户端不能扩大范围。
- 当前和前期的日期都在数据边界内，单个周期最多31天。
- 单次分析固定最多7条聚合查询；每条设置3秒JDBC查询超时与200行聚合结果上限。

3秒是JDBC驱动的超时控制，不是整个HTTP请求必然在3秒内结束。还会有多条SQL、模型调用、网络和报告保存时间。查询预算统计的是分析聚合查询，不包含登录、元数据、历史报告等SQL。

## 分析步骤与证据绑定

| 步骤 | 查询数 | 证据 |
| --- | ---: | --- |
| 当前与前期汇总 | 2 | E1 |
| 主维度当前与前期拆解 | 2 | E2 |
| 两周期的每日趋势 | 1 | E3 |
| 第二维度当前与前期独立拆解 | 2 | E4 |

第二维度是同一筛选范围内的独立拆解，不是与主维度的交叉归因。想进一步看“华东的广告渠道”，使用筛选重查，将华东固定，再按渠道运行新的报告。

金额和订单量的相对变化达到20%、比例变化达到5个百分点时提示波动。这是演示用固定阈值，不是统计显著性、异常预测模型或因果检验。

## Spring AI具体做了什么

1. `PlannerService`调用ChatClient，把自然语言转为类型化Plan。
2. 计划仍经过同一Validator，再展示给用户确认或修改。
3. AnalysisEngine按固定流程完成计算。
4. `NarrativeService`向模型开放当前报告的getMetricDefinition和getEvidence两个只读工具，最多4次工具调用；不增加SQL查询。
5. 模型输出Narrative：定性总结、待验证假设、证据ID和验证方式。
6. 校验结构、文本长度、证据ID和数字；不合格则回退规则解释。

工具中绑定的是本次已授权Core对象，不提供“任意用户/任意报告ID”参数。超过工具预算会抛出异常，配置为直接中断模型解释，防止无限工具循环。

只检查证据ID是否存在，不能在程序层面证明模型的每个语义判断都正确。因此界面仍明确标为“待验证解释”，与Java计算发现分开展示。

## 缓存为什么带这么多字段

同一句“最近收入如何”可能对应不同日期、不同指标，也可能来自只能看华东的用户。因此Key采用：

`固定算法版本 + SHA-256(完整Plan + owner + 授权区域 + dataVersion)`

本机缓存最多256项，普通结果5分钟，空结果1分钟。启用Redis时先查询Redis；异常回退本机缓存或数据库。本版没有分布式单飞/缓存重建锁，突发同Key并发可能重复计算，但不会混合权限。

演示数据是固定快照，应用不提供数据修改API。如手工修改业务表，需要在同一个更新流程中修改dataset_meta.data_version，确保旧缓存不会被误用。生产数据接入应使用一致的ETL快照或版本机制，而不是长期写死版本。

## 可以怎样讲项目

“我做的是一个受控的经营分析Agent。先维护指标口径，把支付额、退款额和净实收拆开，再把自然语言转换成有限的查询计划。所有SQL都由服务端白名单模板生成，每条查询都带数据权限。分析按前期对比、维度拆解和趋势进行，数值由Java计算，模型只做基于证据的辅助解释。金额变化要求分类贡献能与总变化对账；比例变化则用总体分母作贡献分解，避免直接相加百分比。结果带有口径、周期、数据版本和查询证据，可以复核并导出。”

## 高频追问

**为什么不让模型直接写SQL？**

经营指标不只涉及语法，还涉及支付/退款时间和权限。有限指标场景里，结构化Plan与固定模板更容易验证，且能避免任意SQL执行。

**为什么说辅助归因，不说自动找出真实原因？**

聚合变化只能定位变化集中在哪些分类，无法证明活动、天气或人员变化等原因。报告列验证步骤，而不把相关性当因果。

**为什么取消率不能直接平均？**

各区域订单量不同，直接平均会让小样本区域获得过大权重。必须用汇总后的取消订单数除以汇总订单数。

**如何证明没有把其他用户的数据缓存出来？**

查询阶段逐条加权限，缓存Key带用户和授权区域，报告读取还校验归属与当前权限范围。测试包含east用户越权、跨用户读报告以及权限缩小后读取旧报告。

**技术难点对应哪些测试？**

退款跨月、零分母、基期为零、金额/比例贡献对账、数据版本变化导致缓存失效、未知SQL字段拒绝，均有对应自动化测试。实际测试结果见验收记录。

**本项目哪些话不能直接写成成果？**

没有压测就不写QPS或耗时提升百分比；协议桩通过不等于真实模型准确率高；本包虚构订单不等于线上订单量。先实际接入、验证并形成你自己的修改，再把已完成的能力写进简历。
